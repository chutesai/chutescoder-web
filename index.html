Chutes engineering · 2026-08-06

A coding harness that treats context as a variable

chutescoder is a Chutes-owned fork of OpenAI's Codex with a second agent architecture bolted alongside the original one. In RLM mode the model gets exactly one tool — python — running in a persistent IPython kernel that lives for the whole session. Shell, file edits, patches, search, MCP and sub-agents all become ordinary Python functions inside that kernel. Ten tool calls collapse into one cell; a 50k-row result stays addressable as out[7] instead of flooding the context window; and the transcript itself becomes ctx, greppable even for the turns compaction already threw away. Turn the flag off and you have upstream Codex, byte for byte — which is what makes the benchmark honest.

01 — the evidence

Why a new harness

The argument for owning a harness does not depend on anything we have measured. It is already sitting in the public record. Here is one model — Kimi K3 — on one benchmark — Terminal-Bench 2.1 — scored three times by three different organisations.

7.4 points of spread from the harness alone. That is larger than the gap between many adjacent model releases — and two of those three runs used the same harness (Terminus 2) and still differ by 4.1 points. An agentic benchmark does not score a model. It scores a system: model plus scaffold plus retries plus context management. Whoever controls the scaffold controls several points of the result.

The gap is systematic, not noise. Across both models we track, the lab's own harness beats the independent one by a similar margin:

ModelLab harnessAA harnessGap
Kimi K388.3 (KimiCode)85.02−3.3
GLM-5.281.0 (Terminus-2)77.90−3.1

Sources: Moonshot model card, Z.ai model card, Artificial Analysis. All four figures are records in the published-scores table below.

On 2026-08-05 Prime Intellect published Prime Agent, a coding harness whose central claim is exactly this — that the harness matters as much as the model, and that the gains are not benchmark-specific. We found that plausible before testing anything, because the table above already says so. So: if the harness is worth seven points, Chutes should own one — and then measure it honestly rather than assert it.

02 — the design

What chutescoder does

Four ideas, all of them consequences of the same move: stop describing capabilities to the model as tool schemas, and start handing it a programming language with those capabilities already in scope. Below is what the model actually sees.

i

One tool. The rest are functions.

The model's tool list has exactly one entry, python. Every host capability — shell, patches, file IO, ripgrep, web search, MCP — is a Python name in the kernel namespace. Reading twelve files is a for loop, not twelve round trips, and the filtering happens before anything reaches the context window. 

files = [p for p in list_dir("src", depth=3) if p.endswith(".py")]
srcs  = {p: read_file(p) for p in files}
suspects = {p: s for p, s in srcs.items() if "eval(" in s or "exec(" in s}

print(len(files), "files;", len(suspects), "suspects:", list(suspects))
# 812 files; 3 suspects: ['src/plugins/loader.py', ...]

812 files were read. Three lines of output were spent. The other 809 files are still sitting in srcs, addressable, costing nothing.

ii

ctx — the transcript, as data

The host pushes the whole conversation into the kernel as ctx. Because the kernel is never restarted, ctx keeps the turns that compaction summarised away. When the model half-remembers an error from 200 turns ago, it does not guess and it does not re-derive. It greps. 

len(ctx)                     # every turn, including ones no longer in the window
ctx.grep("TimeoutError")     # [(turn_index, line), ...] across the whole session
ctx.dropped                  # turns evicted by compaction — still fully readable here
ctx.slice(100, 140).text()
ctx[42].content

Compaction stops being amnesia and becomes an index. The same mechanism caps cell output: a cell returning 12,000 rows shows the model <list of 12043 dicts — full value kept in out[7]> and a head/tail excerpt. The rows stay in the kernel.

iii

Delegation is a function call

await rlm(...) spawns a sub-agent with its own model, its own kernel and its own context window. It reads 200k tokens; the parent gets back a paragraph. When the work is independent, fan out — the kernel runs cells under IPython's autoawait, so concurrent host calls really are concurrent. 

answer = await rlm("Read src/auth/** and explain how sessions are validated")

# fan out over independent work
findings = await rlm.map([f"Audit {m} for SQL injection" for m in modules],
                         concurrency=6)

# or keep the handles, and steer a child mid-flight
handles = [await rlm.spawn(f"Audit {m}") for m in modules]
await agent_message.send("skip the vendored deps",
                         receiver_name=handles[0].session_name)

A sub-agent is the cheapest way to look at something large: you pay for the summary, not for the reading.

iv

The harness edits itself

rlm.harness is the state that shapes the agent — prompt notes, sub-agent definitions, skills, memories. The agent can change it mid-task; the change lands in the system prompt on the next turn and persists across sessions. Write a memory the moment you learn something that cost you time. Write a skill once you have done the same multi-step thing twice. 

rlm.harness.create_memory("flaky-network-test",
    "tests/net/test_retry.py fails ~1 in 5 on first run; re-run before investigating")

rlm.harness.create_skill("release",
    description="cut a release of this repo",
    body="1. bump version in Cargo.toml\n2. cargo test --all\n3. git tag -s v$VERSION")

rlm.harness.list("skill")             # name + description of every skill
rlm.harness.read("skill", "release")  # load the body only when you need it

Listings are cheap and always in the prompt; bodies are loaded on demand. That is what keeps a growing skill library from eating the context window it was meant to save.

03 — the implementation

How it's built

The guiding principle was add a runtime, don't replace the agent. chutescoder does not fork Codex's turn loop, its sandbox or its tool registry. It adds a Python sidecar beside the existing runtime and routes every capability back through the tools Codex already had — so the approval policy, the execpolicy sandbox and the audit trail are unchanged.

A fork, not a rewrite

chutescoder is a fork of openai/codex (Apache-2.0), published at chutesai/chutescode. The RLM harness is a new crate, codex-chutes-rlm, sitting next to the existing ones.

apply_patch stays visible

Even in RLM mode. Models are heavily trained on its freeform format, and forcing it through a Python string literal costs accuracy for nothing. Purity is not a goal here; scores are.

State survives restarts

The namespace is snapshotted per-variable with dill. On reboot the model is told what came back and what didn't, rather than silently losing a variable it is still reasoning about.

Tested before it was believed

33 Python checks drive the real kernel against a mock host; 43 Rust tests cover the protocol, kernel supervisor and continual harness, 12 of them against the live sidecar.

04 — measured

The controlled harness A/B

This is the only measured data on this page, and it is not the headline experiment. It is a cheap, fully-controlled test of the one variable the RLM design is about, run while the Rust build was still going. Identical model, task, corpus, turn budget, temperature and endpoint. The only thing that changes is how the model reaches its tools.

Read this before reading the numbers

This is not chutescoder versus upstream Codex. That comparison needs both real binaries driven through Sandy on a standard benchmark, and it has not been run — see Benchmarks, where every cell is still empty. What follows is a mechanism study: n = 1–3 trials per cell, one model, five synthetic tasks. Directional, not publishable. Anyone citing this work should say "controlled mechanism study, n small, one model" — not "chutescoder beats Codex".

What it actually says

the harness loses

1. On tasks a single grep answers, RLM is pure overhead

needle is the clearest case: CLASSIC solved it in one tool call and 946 input tokens, against RLM's 6,246. Almost all of the difference is the ~5 KB RLM prompt, paid on every single request whether the task needs it or not. Reported first because it is the honest shape of the result: this harness is not free, and it does not pay for itself on easy retrieval.

the harness wins

2. Where intermediate results must be combined, it wins

join needs 180 files parsed, dependency sets built and 16,110 pairs compared: 2.5 turns vs 4.0 and 1.5 tool calls vs 3.0. One cell does the parse, the join and the argmax; the conventional arm needs a turn to orient, a turn to look and a turn to compute.

it depends

3. After compaction, the advantage tracks whether compaction was actually lossy

With 5 facts, RLM used 30% fewer turns and 58% fewer tool calls — but both arms scored 3/3, because a competent summariser simply kept all five facts. Efficiency, not accuracy. Reporting that as a capability win would have been overclaiming.

So it was rerun with 40 facts — more than a concise summary can hold. Now an accuracy gap appears: RLM 3/3 vs CLASSIC 2/3, alongside 27% fewer turns, 42% fewer tool calls and half the wall clock. The failing CLASSIC trial burned all 20 turns and 49,875 tokens searching a filesystem that no longer held the answer, and finished wrong. The RLM arm reached its own evicted history with ctx.grep.

One failure in three is a small sample. The honest reading is "consistent with the predicted mechanism", not "a 33-point accuracy win".

the uncomfortable finding

shell is already a programmatic escape hatch

CLASSIC did not lose join by brute force. It won its way to the same answer by writing a python -c one-liner through its shell tool. Every serious coding agent has a shell, so "it can loop" is not the advantage — the baseline can loop too. This narrows the claim considerably, and it should be narrowed. The marketing version of programmatic tool calling oversells against baselines that already have a REPL one bash -lc away.

What the baseline genuinely cannot do, and what the measurements above are actually about:

  • Keep state across turns. Its shell is stateless — every invocation starts over. The RLM kernel still holds deps on the next turn.
  • Avoid re-paying for output. A shell result lands in the context window in full. A cell's result can stay in the kernel as out[N] and be sliced later for free.
  • Reach into evicted history. This is where the real claim lives, and it is the only thing recall-40 tests.
Every measured cell, and where the raw records live

What is still untested here
  • Every task finishes in 2–20 turns, far short of a real context window. Compaction is forced synthetically rather than reached naturally.
  • One model. GLM-5.2 could not be run at all — see the blocked cells below.
  • Sub-agent delegation (rlm(...)) and /refine are not implemented yet, so neither is exercised.
  • Five synthetic tasks are not a benchmark. The adapters for Terminal-Bench, SWE-Bench Pro, OOLONG, AA-LCR and S-NIAH exist in the repaired bench-runner; the runs have not been executed.

    06 — the experiment

    Benchmark results

    This is the experiment the project set out to run, and it is the one that has not been run. The A/B above is a controlled proxy for the mechanism; this is the product comparison, and it needs the built binary driven through Sandy against real benchmarks. The adapters exist in the (now repaired) bench-runner. The runs do not.

    The model is the control; the harness is the independent variable. Arms B and C run the same binary lineage, the same model endpoint, the same sandbox (Sandy), the same task set, the same seed and the same wall-clock and step budget. The only difference is the tool surface and the prompt that describes it. Arm A exists to check that our pipeline reproduces the published numbers at all — if it doesn't, our absolute scale is internal-only and we will say so.

    Loading results…

    A fault we found on the way, that would have produced two plausible-looking zeros

    Before any arm could run, responses.chutes.ai turned out to be unable to do multi-turn tool calling with Kimi K3. The first tool call worked; replaying the result back failed with "Kimi K3 tool messages need a resolvable tool name." The model was not at fault — the identical conversation succeeds against llm.chutes.ai. The proxy was dropping the assistant tool_calls message when replaying history, so the generated chat request was literally [user, tool]: nothing to match by order, and no name.

    This capped every agent using Kimi K3 through that endpoint at a single tool call — including Codex itself and Sandy's built-in codex agent, which is exactly what the bench-runner's Terminal-Bench adapter drives. It would have broken arm B and arm C identically, which is the kind of fault that yields two believable zeros instead of an error. Fixed in chutesai/responses-proxy PR #1 with 13 regression tests that assert on the generated chat messages; the reproduction was proven against a pristine checkout first.

    responses.chutes.ai itself was not touched — it is shared production infrastructure, so the fix is a PR awaiting review. Details: docs/RESPONSES_PROXY_FIX.md.

    What we record for every cell, and why an empty cell stays empty
    • score, in the benchmark's native metric
    • n attempted / n in the full benchmark / subset seed
    • total tokens in and out, and cost — a harness that wins by spending 6× the tokens has not obviously won
    • wall clock, and steps or turns used
    • harness commit sha, model id, and the bench-runner run id
    • failure taxonomy for non-passes: timeout / context exhaustion / tool error / wrong answer

    Full runs of Terminal-Bench and SWE-Bench Pro across two models and two arms are far past the available budget, so those two use a fixed random subset of at least 10% of tasks with the same seed across every arm, making the arms paired. Any subset result is labelled preliminary and is never presented as a full-benchmark score.

    A run with more than 5% unrecovered infrastructure errors is discarded and re-run rather than reported. Until a cell has a real, scored, non-discarded run behind it, it renders as pending — because an empty cell is correct and an invented number is not.

    Two things worth stating plainly

    Neither lab publishes SWE-bench Verified. It is the benchmark most people mean by "coding score", and there is no entry for either model — not on the model cards, not on swebench.com. Moonshot reports DeepSWE, FrontierSWE and SWE-Marathon; Z.ai reports SWE-bench Pro. They do not overlap.

    AA-LCR is the only public long-context number that exists for either model. MRCR, RULER, LongBench v2, OOLONG, Fiction.LiveBench and every NIAH variant are unpublished for both, despite both models shipping a 1,048,576-token context. Two models with million-token windows and exactly one shared long-context datapoint between them is itself a decent argument for running your own evals.

    One more caveat we are keeping in view rather than hiding: AA's tau2-bench value for GLM-5.2 (99.12%) sits far above every peer and is almost certainly not a full run. It is shown in the table because it is in the source data, and flagged here because it should not be cited. Similarly, MCP-Atlas for GLM-5.2 appears twice — 82.6 per Moonshot, 76.8 per Z.ai. Where a lab's own card and a rival's disagree, prefer the lab's own.
