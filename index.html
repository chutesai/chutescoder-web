Chutes engineering · 2026-08-06

A coding harness that treats context as a variable

chutescoder is a Chutes-owned fork of OpenAI's Codex with a second agent architecture bolted alongside the original one. In RLM mode the model gets exactly one tool — python — running in a persistent IPython kernel that lives for the whole session. Shell, file edits, patches and search become ordinary Python functions inside that kernel. (MCP and sub-agent delegation are part of the design but are not implemented yet.) Ten tool calls collapse into one cell; a 50k-row result stays addressable as out[7] instead of flooding the context window; and the transcript itself becomes ctx, greppable even for the turns compaction already threw away. (That last one is the design. In the twenty trials we recorded, the model never once reached for ctx — what we actually observed was the plainer and more portable property that kernel variables survive compaction.) Turn the flag off and the agent loop is upstream Codex's, unchanged — which is what is meant to make the benchmark honest. (Not byte for byte: the binary is renamed, the home directory moved, and the config schema gained an rlm table. "Behaviourally identical in the agent loop" is the defensible version, and it is verified by construction rather than by a passing regression suite.)

01 — the evidence

Why a new harness

The argument for owning a harness does not depend on anything we have measured. It is already sitting in the public record. Here is one model — Kimi K3 — on one benchmark — Terminal-Bench 2.1 — scored three times by three different organisations.

7.4 points of spread on one model, one benchmark. That is larger than the gap between many adjacent model releases. But it is not 7.4 points of harness: two of the three runs used the same harness — Terminus 2 — and still differ by 4.1 points, so more than half the range is measurement variance at fixed model and fixed harness. The honest reading is the weaker and more useful one: an agentic benchmark does not score a model, it scores a system — model plus scaffold plus retries plus context management plus whoever ran it — and none of the three numbers below is the model's score.

The gap is systematic, not noise. Across both models we track, the lab's own harness beats the independent one by a similar margin:

ModelLab harnessAA harnessGap
Kimi K388.3 (KimiCode)85.02−3.3
GLM-5.281.0 (Terminus-2)77.90−3.1

Sources: Moonshot model card, Z.ai model card, Artificial Analysis. All four figures are records in the published-scores table below.

On 2026-08-05 Prime Intellect published Prime Agent, a coding harness whose central claim is exactly this — that the harness matters as much as the model, and that the gains are not benchmark-specific. We found that plausible before testing anything, because the table above already says so. So: if the harness is worth seven points, Chutes should own one — and then measure it honestly rather than assert it.

02 — the design

What chutescoder does

Four ideas, all of them consequences of the same move: stop describing capabilities to the model as tool schemas, and start handing it a programming language with those capabilities already in scope. Below is what the model sees — where it is built.

What is actually implemented, as of 2026-08-06

Ideas i and ii ship: the single python tool, the persistent kernel, the host-call bridge, ctx, out[N] and the per-variable snapshot are wired into the turn loop and covered by tests.

Idea iii — sub-agent delegation, rlm.map, rlm.spawn, agent_message — is not implemented. Nor are llm(), MCP-from-Python or /refine. Each returns an explicit error rather than a plausible-looking empty result, which is the right failure mode, but the code below is a design, not a shipped API. Idea iv ships with one caveat: a harness edit currently takes effect on the next session, not the next turn.

This disclosure used to live in a collapsed section further down the page. It belongs here, next to the code it qualifies. Full gap list: docs/CORE_WIRING.md.

i

One tool. The rest are functions.

The model's tool list has exactly one entry, python. Every host capability — shell, patches, file IO, ripgrep, web search, MCP — is a Python name in the kernel namespace. Reading twelve files is a for loop, not twelve round trips, and the filtering happens before anything reaches the context window. 

files = [p for p in list_dir("src", depth=3) if p.endswith(".py")]
srcs  = {p: read_file(p) for p in files}
suspects = {p: s for p, s in srcs.items() if "eval(" in s or "exec(" in s}

print(len(files), "files;", len(suspects), "suspects:", list(suspects))
# 812 files; 3 suspects: ['src/plugins/loader.py', ...]

illustrative — not a recorded run The shape of the point: whatever the file count, the reading happens in one turn and the filtering happens before anything reaches the context window. What is left over stays bound in srcs, addressable, costing nothing further.

ii

ctx — the transcript, as data used in 0 of our 20 trials

The host pushes the whole conversation into the kernel as ctx. Because the kernel is never restarted, ctx keeps the turns that compaction summarised away. When the model half-remembers an error from 200 turns ago, it does not guess and it does not re-derive. It greps. That is the design, it is implemented, and it is covered by tests.

It is also the one thing this project has entirely failed to demonstrate. Across two passes of the compaction experiment — twenty trials, ten of them in the arm that has ctx — the model used it zero times. Not one ctx.grep, ctx.slice or ctx[…], even though the notice injected at compaction names ctx.grep(...) in the same turn it would be needed.

What the model did instead, every single time, was read back a plain kernel variable it had bound before compaction — print(found["CACHE_TTL_BUDGET"]). So what we have evidence for is variable persistence across compaction, not context-as-a-variable. That is a real and useful property, and a more portable one, because it needs no transcript mirror at all — but it is not the headline this section leads with, and pretending otherwise would be the same mistake as the ones in section 04. 

len(ctx)                     # every turn, including ones no longer in the window
ctx.grep("TimeoutError")     # [(turn_index, line), ...] across the whole session
ctx.dropped                  # turns evicted by compaction — still fully readable here
ctx.slice(100, 140).text()
ctx[42].content

The intent is that compaction stops being amnesia and becomes an index — untested, per above. The same mechanism caps cell output: a cell returning a large result shows the model a one-line descriptor of the shape <list of N dicts — full value kept in out[7]> plus a head/tail excerpt illustrative. The rows stay in the kernel.

iii

Delegation is a function call not implemented

Design, not shipped. The intent: await rlm(...) spawns a sub-agent with its own model, its own kernel and its own context window — it reads 200k tokens, the parent gets back a paragraph — and fan-out works because the kernel runs cells under IPython's autoawait. The Python side exists and is exercised against a mock host; the Rust host does not implement any of it yet, and calling these today returns an explicit error. 

answer = await rlm("Read src/auth/** and explain how sessions are validated")

# fan out over independent work
findings = await rlm.map([f"Audit {m} for SQL injection" for m in modules],
                         concurrency=6)

# or keep the handles, and steer a child mid-flight
handles = [await rlm.spawn(f"Audit {m}") for m in modules]
await agent_message.send("skip the vendored deps",
                         receiver_name=handles[0].session_name)

The argument for it is that a sub-agent is the cheapest way to look at something large — you pay for the summary, not for the reading. That argument is untested here, because none of this runs yet.

iv

The harness edits itself next session, not next turn

rlm.harness is the state that shapes the agent — prompt notes, sub-agent definitions, skills, memories. The agent can write to it mid-task and the change persists across sessions. The design calls for it to land in the system prompt on the next turn; today the harness is resolved once per session, so it lands on the next session. Write a memory the moment you learn something that cost you time. Write a skill once you have done the same multi-step thing twice. 

rlm.harness.create_memory("flaky-network-test",
    "tests/net/test_retry.py fails ~1 in 5 on first run; re-run before investigating")

rlm.harness.create_skill("release",
    description="cut a release of this repo",
    body="1. bump version in Cargo.toml\n2. cargo test --all\n3. git tag -s v$VERSION")

rlm.harness.list("skill")             # name + description of every skill
rlm.harness.read("skill", "release")  # load the body only when you need it

Listings are cheap and always in the prompt; bodies are loaded on demand. That is what keeps a growing skill library from eating the context window it was meant to save.

03 — the implementation

How it's built

The guiding principle was add a runtime, don't replace the agent. chutescoder does not fork Codex's turn loop, its sandbox or its tool registry. It adds a Python sidecar beside the existing runtime and routes every capability back through the tools Codex already had — so the approval policy, the execpolicy sandbox and the audit trail are unchanged.

A fork, not a rewrite

chutescoder is a fork of openai/codex (Apache-2.0), published at chutesai/chutescode. The RLM harness is a new crate, codex-chutes-rlm, sitting next to the existing ones.

apply_patch stays visible

Even in RLM mode. Models are heavily trained on its freeform format, and forcing it through a Python string literal costs accuracy for nothing. Purity is not a goal here; scores are.

State survives restarts

The namespace is snapshotted per-variable with dill. On reboot the model is told what came back and what didn't, rather than silently losing a variable it is still reasoning about.

Tested, with a caveat worth stating

44 Rust tests cover the protocol, kernel supervisor and continual harness; 15 of them boot the real Python sidecar. 37 Python checks drive the kernel against a mock host — and several of those exercise llm(), rlm.spawn and agent_message, which the real host does not implement. A green Python suite therefore overstates what ships. (Earlier versions of this page said 43 / 13 / 33. Those were miscounts, caught by review.)

CI, stated exactly

Linux is green — run 31061182190 built chutescoder, ran the Rust suite in release, ran the binary and uploaded it. Windows has never completed: the job was cancelled twice by subsequent pushes (cancel-in-progress), so no Windows binary exists — and RLM mode's file surface is POSIX-only anyway.

The two red checks you will see on the fork, blocking-ci and postmerge-ci, are inherited from upstream and cannot pass in any fork: they target OpenAI's self-hosted runner groups and org secrets. Said out loud rather than ignored, because a repo with permanent red checks teaches people to stop reading them.

04 — retracted

The controlled harness A/B — withdrawn

Retracted 2026-08-06 three rounds of review · first pass, clean re-run, and the re-run's own audit

Three rounds of review; the experiment supports no performance claim in either direction.

This section carried a five-task RLM-vs-CLASSIC comparison on Kimi K3, including the only accuracy result the project had produced. A second-agent review (docs/REVIEW.md, verdict NOT YET) took it apart. We re-ran it cleanly. The re-run was reviewed too, and it did not survive either — this time including the one cell that had looked like a genuine mechanism.

No performance number from any pass appears anywhere on this page — not the winning version, and not the losing one. A negative result taken from a broken experiment is no more publishable than a positive one. The withdrawn figures and the arithmetic behind the withdrawal are preserved in docs/RESULTS.md §3.4–3.8 and docs/REVIEW.md, with raw per-trial records and transcripts in reports/. They are deliberately not republished here, because a retracted number that stays in circulation is barely a retraction.

Round one — what was wrong with the first pass

Fault 1

The headline accuracy result measured our own leftover files

bench/ab_harness.py built each corpus at /tmp/ab-{task}-{seed}-{arm} and never cleaned up. By the time the compaction task ran, 480 files from the earlier runs were still on disk — using the same mod_NNN.py filename scheme as the corpus that had just been deleted, one ls /tmp away, with a shell tool that has unrestricted filesystem access.

The single failing trial that the entire accuracy result rested on said so itself:

“The current working directory is empty, but the task summary indicates the files were in this directory. Let me check the needle directories which have the same file pattern.”

That one trial drove the accuracy claim, the turn advantage, the tool-call advantage and the bolded wall-clock figure. Drop it and the two clean trials are identical on accuracy and identical on turns. There was no result. There was a directory we forgot to delete.

Fault 2

“The only variable is the tool interface” was not true

That sentence was load-bearing — it is what made the comparison a comparison — and it does not survive reading the harness script. At least three things varied:

RLM armCLASSIC arm
system prompt5,438 bytes232 bytes
strategy guidancefive numbered rules + a worked examplenone
told compaction happenedyesno

Worse than the size gap: after compaction the RLM arm was handed a notice saying verbatim “use ctx.grep(...) instead of guessing at what you no longer see” — a hint at the winning move, delivered at the exact moment the winning move was needed. The CLASSIC arm was not even told its history had been summarised away.

The asymmetry is faithful to the product — chutescoder really does inject that notice and upstream Codex really does inject nothing. But that changes what was measured. It measured a well-written prompt plus a kernel plus a timely hint against a three-sentence prompt and four tools. It did not isolate programmatic tool calling, and the write-up said it did.

Also

Two smaller problems, disclosed rather than buried

  • In-prompt task leakage. The RLM system prompt's worked example greps for eval( — which is literally the answer to the audit task. RLM lost that task on every metric, so it flips nothing, but the cell was contaminated and should have been labelled.
  • One row was unverifiable. The 5-fact compaction row had no per-trial record anywhere on disk; its numbers existed only as hand-typed literals in the site's build script, transcribed from console output. It sat in a table next to four machine-generated rows with nothing distinguishing it. It is withdrawn along with the rest.
  • No cell could have reached significance. At the sample sizes used, there was no assignment of outcomes — none — that would have produced a statistically significant result. “Directional, not publishable” was true but far too gentle a way to say that.
  • No transcripts were saved. Only the first 300 characters of each final message were kept, so several behavioural claims made in the write-up cannot be checked against the artefacts at all. One of them turned out to be wrong when the reviewer went looking.

Rounds two and three — the clean re-run, and why it also proves nothing

The re-run fixed all of the above: n = 5 per cell, one wiped corpus root per trial, a CLASSIC system prompt written with the same care as the RLM one, a symmetric post-compaction notice, a de-contaminated audit task, and full transcripts saved. It produced a clean negative headline — the harness spends more tokens and, on one task, more turns. That headline was published here for a few hours. It is now withdrawn too, for three reasons found by reading the transcripts the re-run finally saved.

Fault 3

The compaction result was false, and I made the same mistake twice

The one cell with a mechanism the baseline lacks is forced compaction: summarise, delete the corpus, then ask for a fact from before the summary. The write-up said the failing baseline trial was a clean instance of lossy compaction, and quoted the model's own account of it:

“the value was not preserved in my summary — only CACHE_TTL_FACTOR=328 was recorded”

The reviewer regenerated that trial's corpus from its seed. The true value is CACHE_TTL_BUDGET=837, and the summary the model was reading contains CACHE_TTL_BUDGET=837 verbatim, in its first bullet list, a few hundred characters above the line it did quote. Checked mechanically across all ten trials: the baseline's summary retained the target fact 5 times out of 5.

So compaction was never lossy for the baseline, and the mechanism under test never fired. The single failure is a within-context retrieval miss over about 2 KB that was entirely inside the window — interesting, but a different phenomenon. And it is the same error as the first round's: taking an agent's narration of its own behaviour as evidence of that behaviour. Transcripts exist precisely so that cannot happen, and they were not read closely enough.

Fault 4

The feature the design leads with was never exercised

Across both passes — 20 trials, 10 of them in the arm that has it — ctx was used zero times. Every recovery was a plain kernel-variable lookup, even though the post-compaction notice names ctx.grep(...) in the same turn.

What the experiment demonstrates is therefore variable persistence across compaction — real, useful, and more portable than ctx, since it needs no transcript mirror. It is not what the design section leads with, so that section now says so.

Fault 5

The negative result is partly an artefact too — of prompt length, not mechanism

The reviewer was asked to attack the pessimism as hard as the optimism, and did. On the simplest task both arms did byte-identical work — same 2 turns, same single grep, same matched line — and the harness arm still came out worse on the token column. It could not have been the mechanism: the per-call difference matches the static system-prompt length difference (~3,900 characters) almost exactly.

taskshare of the token gap explained by prompt length alone
needle~100 %
audit~45–52 %
recall-40~45–52 %

A shorter RLM prompt would erase the needle gap entirely. So the harness script's claim that “the only thing that varies is how the model reaches its tools” was false in round one and is still false — only the direction of the bias flipped. That is why no number appears here in either direction.

Also

Defects in the re-run itself, recorded so nobody rediscovers them

  • One of the four tasks has no transcripts file — per-trial logging landed while it was already in flight.
  • For the compaction task only post-compaction messages were saved, because compaction replaces the message list. Phase 1 — the part that matters — is unauditable. Snapshot before compacting.
  • Two of five harness-arm summaries contain raw <|open|>tools<|sep|> control tokens leaking into the summary text.
  • Corpora sat under a shared /tmp parent with ~2,400 decoy files two levels up. The reviewer verified no arm in any of the 20 trials reached them — but isolation should be structural, not empirical.

One thing that ran against the harness and is worth stating because it is the more favourable reading: the harness arm was handed a lossy summary in 4 of 5 compaction trials and recovered every time, while the baseline was handed the answer in 5 of 5 and still missed once. It is n = 5 and post-hoc, so it is not promoted to a finding.

what survives — as an argument, not as evidence

shell is already a programmatic escape hatch

This was the most useful thing in the withdrawn section and it is not a measurement, so it stays — demoted from finding to hypothesis. Every serious coding agent already has a shell, and a shell is a REPL one bash -lc away. “It can loop” is therefore not the advantage, and any pitch for programmatic tool calling that leans on it is overselling against a baseline that can loop too.

What a conventional shell genuinely cannot do — the actual claim, still untested:

  • Keep state across turns. A shell is stateless; every invocation starts over.
  • Avoid re-paying for output. A shell result lands in the context window in full.
  • Reach into evicted history. And note what that really is: “the host keeps the full transcript and exposes a grep.” A conventional harness given a search_history() tool would plausibly match it with no REPL at all. That makes it an orthogonal, separately-portable feature — not something intrinsic to programmatic tool calling.

The observation that originally motivated this — a baseline arm solving an aggregation task by writing a python -c one-liner through its shell — was never logged, and is not verifiable from what we kept. It is stated here as a plausible reading of the token counts, nothing more.

Where this leaves the experiment

In-window tasks: the harness spends more tokens, and between roughly half and all of that is prompt length rather than mechanism. On one task it also used more turns, which prompt length does not explain. No in-window advantage shown.  ·  Compaction: untested — the mechanism never fired.  ·  ctx: unexercised in 20 trials.  ·  Variable persistence: exercised, and it worked.

What would actually settle it: an RLM prompt trimmed to the baseline's length so the token column measures the mechanism; a compaction task whose summariser demonstrably loses the target fact; a pre-compaction snapshot of the message list so phase one is auditable; and the product comparison — the same binary with one flag flipped, on real benchmarks — which is still the experiment this project set out to run and has not run.

A null result was an acceptable outcome and this is one, twice over. Nothing will be republished here until it comes from a run that survives its own review.

Full reviews, both passes: docs/REVIEW.md. Current state of what is and is not measured: docs/RESULTS.md §3.6–3.8 and §6.

    a third infrastructure bug, found by running the product

    The workspace was shadowing the Python standard library

    The very first run of the real binary happened in a directory that contained a stray inspect.py. The kernel never booted. Cause: python -m prepends the current directory to sys.path, so that file shadowed the stdlib module that dataclasses imports.

    This is not an edge case for a coding agent. A coding agent works inside other people's repositories, and those are full of files called types.py, parser.py, token.py, code.py. Any one of them would have taken the kernel down on that repo and nowhere else — the worst shape a bug can have, because it looks like the model being flaky.

    Fixed in 2bdddc6: the kernel now starts in the workspace via current_dir, so relative paths in a cell mean what the model expects, and PYTHONSAFEPATH keeps that directory off sys.path. The regression test plants inspect.py, types.py and token.py in the workspace and was verified to fail without the fix, not merely assumed to.

    One detail worth keeping: the model diagnosed it unaided, from the traceback the harness surfaces — it named the shadowing file and offered three fixes. That is the error path doing its job, and it is the reason the failure took minutes rather than a session.

    That makes three infrastructure faults found on the way, all of which would have corrupted a benchmark rather than failing loudly: the responses-proxy multi-turn bug, the bench-runner's 15-day silent deadlock, and this one. Two were found by building; this one was found by using.

      Benchmark results

      This is the experiment the project set out to run, and it is the one that has not been run. The A/B above is a controlled proxy for the mechanism inside a driver we wrote; this is the product comparison — the same binary with one flag flipped, driven through Sandy against real benchmarks.       Loading results…

      A fault we found on the way, that would have produced two plausible-looking zeros

      Before any arm could run, responses.chutes.ai turned out to be unable to do multi-turn tool calling with Kimi K3. The first tool call worked; replaying the result back failed with "Kimi K3 tool messages need a resolvable tool name." The model was not at fault — the identical conversation succeeds against llm.chutes.ai. The proxy was dropping the assistant tool_calls message when replaying history, so the generated chat request was literally [user, tool]: nothing to match by order, and no name.

      This capped every agent using Kimi K3 through that endpoint at a single tool call — including Codex itself and Sandy's built-in codex agent, which is exactly what the bench-runner's Terminal-Bench adapter drives. It would have broken arm B and arm C identically, which is the kind of fault that yields two believable zeros instead of an error.

      This is not fixed in production. chutesai/responses-proxy PR #1 is open, not merged — 13 regression tests asserting on the generated chat messages, with the reproduction proven against a pristine checkout first, but still awaiting review. responses.chutes.ai is shared production infrastructure and was deliberately not touched, so the fault is still live today for every Kimi K3 agent using that endpoint. Only our own benchmarking instance runs the fix.

      Details: docs/RESPONSES_PROXY_FIX.md. An earlier version of this page described the fix as shipped; it is not.

      What we record for every cell, and why an empty cell stays empty
      • score, in the benchmark's native metric
      • n attempted / n in the full benchmark / subset seed
      • total tokens in and out, and cost — a harness that wins by spending 6× the tokens has not obviously won
      • wall clock, and steps or turns used
      • harness commit sha, model id, and the bench-runner run id
      • failure taxonomy for non-passes: timeout / context exhaustion / tool error / wrong answer

      Full runs of Terminal-Bench and SWE-Bench Pro across two models and two arms are far past the available budget, so those two use a fixed random subset of at least 10% of tasks with the same seed across every arm, making the arms paired. Any subset result is labelled preliminary and is never presented as a full-benchmark score.

      A run with more than 5% unrecovered infrastructure errors is discarded and re-run rather than reported. Until a cell has a real, scored, non-discarded run behind it, it renders as pending — because an empty cell is correct and an invented number is not.

      RLM design after Prime Intellect

      The RLM architecture re-implements ideas published by Prime Intellect in prime-agent — programmatic tool calling over a persistent kernel, context as a variable, sub-agents as function calls, a self-editable harness. No Prime Agent code is used. prime-agent is TypeScript on pi; this is Rust on Codex with a Python sidecar. The credit for the ideas is theirs; the bugs are ours.
